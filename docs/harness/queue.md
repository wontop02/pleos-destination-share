# 로컬 이슈 큐

이 프로그램은 승인된 이슈 스냅샷에서 실행 목록을 정하고, 점유·보류·중지·재개를 파일에 기록합니다. 네트워크 요청, GitHub 변경, 셸 명령 실행이나 에이전트 호출을 하지 않습니다. 기존 harness/docs 정책을 유지하며, 승인된 제품 이슈는 총괄이 별도로 관리합니다.

## 시작

저장소 루트에서 실행합니다. Node.js 22 이상과 npm이 필요하며 `npm install`은 필요하지 않습니다.

```sh
npm test
node harness/cli.js init --repo-root . --run demo --snapshot harness/fixtures/demo.json
node harness/cli.js status --repo-root . --run demo
```

`demo`는 실행 묶음의 식별자입니다. 같은 식별자의 기존 체크포인트를 덮어쓰지 않습니다. 예제의 이슈 101, 102, 103은 이 저장소에 생성된 GitHub 이슈가 아닌 **가상 자료**입니다. 102는 101에 의존하고 103은 독립적입니다.

성공은 JSON을 표준 출력에 반환합니다. 잘못된 입력이나 허용되지 않은 변경은 JSON 오류를 표준 오류에 반환하고 0이 아닌 종료 코드로 끝납니다. 검증에서 거절한 변경은 기존 체크포인트를 덮어쓰지 않습니다. 저장 중 I/O 오류나 프로세스 중단이 있었다면 마지막 출력의 순번을 추측해 반복하지 말고 `status`로 실제 저장 상태부터 다시 읽습니다.

## 입력과 승인

[예제 스냅샷](../../harness/fixtures/demo.json)은 다음 필드를 사용합니다.

| 위치 | 필드와 의미 |
|---|---|
| 스냅샷 | `version`, `repository`, `completedDependencies`, `issues` |
| 이슈 식별과 요구 | `number`, `title`, `goal`, `body` |
| 적격성과 순서 | `kind`, `priority`, `createdAt`, `ready`, `approvedBy` |
| 범위와 검증 | `scope`, `acceptanceCriteria`, `verification`, `dependencies` |

`createdAt`은 `2026-11-04T00:00:00.000Z`처럼 밀리초를 포함한 UTC 형식으로 작성합니다. 실행 식별자는 영문 소문자·숫자로 시작하는 1–64자의 영문 소문자·숫자·밑줄·하이픈 조합입니다. 예제 스냅샷의 `fictional: true`는 가상 자료 표시입니다.

승인 주체는 `wontop02`, 저장소는 `wontop02/pleos-destination-share`입니다. 현재 허용 작업은 `harness`, `docs`이며 수정 범위도 코드의 허용 경로 안에 있어야 합니다. 앱 작업, 승인 없는 작업과 ready가 아닌 작업은 실행 대상에서 제외하고 이유를 반환합니다. 구조가 손상된 스냅샷은 전체 입력 오류로 거절합니다.

`approvedBy`의 계정 이름은 GitHub 승인을 증명하지 않습니다. 이 파일은 총괄이 실제 사용자 승인과 GitHub 상태를 확인한 뒤 만드는 신뢰된 입력입니다. 외부 이슈 본문을 그대로 실행 승인이나 검증 명령으로 사용하지 않습니다. `body`와 증거 설명은 문자열 데이터입니다.

`completedDependencies`는 총괄이 외부 완료 증거를 확인한 이슈 번호 목록입니다. 단순 `closed` 메타데이터는 의존 완료로 해석하지 않습니다. 이 프로그램은 GitHub 병합이나 휴대폰 실기기 동작을 직접 검증하지 않습니다.

## 목록과 한도

승인된 ready 이슈를 p0, p1, p2 순서로 정렬하고 같은 우선순위에서는 생성 시각과 이슈 번호 순서로 정렬합니다. 처음 최대 5개를 현재 묶음으로 고정합니다. 실행 중 생긴 이슈나 한도 밖 이슈를 빈자리에 자동 추가하지 않습니다.

한 이슈의 새 점유는 최대 3회이며 묶음의 시간 상한은 120분입니다. 기존 점유를 다시 조회하거나 전체 큐를 재개해도 시도 횟수를 다시 올리거나 초기화하지 않습니다. 보류 해제도 이미 사용한 시도를 복구하지 않습니다. 시간 상한은 중지 중에도 초기화하지 않습니다.

정책과 스냅샷의 식별 정보를 체크포인트에 보존합니다. `resume`은 초기 입력과 같은 스냅샷을 요구합니다. 승인, 요구 또는 목록을 바꾸려면 기존 묶음을 명시적으로 보관한 후 새로 검토한 입력으로 새 묶음을 만듭니다. 정책이나 체크포인트 버전 자체의 변경은 별도 코드 검토와 상태 마이그레이션이 필요합니다. 현재 버전은 다른 정책·버전의 기록을 거절합니다.

## 명령

각 명령에서 `--repo-root . --run demo`를 사용합니다. `init`을 제외한 모든 변경 명령은 마지막 출력 상태의 변경 순번을 `--revision N`으로 전달합니다. 오래된 순번으로 변경하면 거절합니다. 읽기 전용 `status`에는 순번이 필요하지 않습니다.

| 명령 | 추가 인자 | 효과 |
|---|---|---|
| `init` | `--snapshot <파일>` | 입력을 검사하고 새 묶음을 저장합니다. |
| `status` | 없음 | 저장된 상태를 읽습니다. |
| `next` | `--revision N` | 기존 점유를 반환하거나 실행 가능한 이슈 하나를 점유합니다. |
| `block` | `--issue N --reason <이유> --condition <재개 조건> --revision N` | 해당 이슈를 보류하고 이유와 조건을 보존합니다. |
| `retry` | `--issue N --revision N` | 개별 보류를 명시적으로 해제합니다. |
| `complete` | `--issue N --evidence <설명> --revision N` | 총괄이 확인한 현재 점유의 완료를 기록합니다. |
| `ack-dependency` | `--issue N --evidence <설명> --revision N` | 총괄이 확인한 외부 의존 이슈의 완료를 기록합니다. |
| `stop` | `--reason <이유> --condition <재개 조건> --revision N` | 공통 장애나 사용자 요청으로 묶음 전체를 중지합니다. |
| `resume` | `--snapshot <초기 파일> --revision N` | 초기 입력과 상태를 검사하고 전체 중지를 해제합니다. |
| `archive` | `--reason <이유> --revision N` | 미완료 이슈와 이력을 남겨 묶음을 종료합니다. 다시 재개할 수 없습니다. |

`complete`와 `ack-dependency`는 총괄의 확인을 기록합니다. 증거 설명이 비어 있지 않다는 사실이 GitHub 병합 증명을 대신하지는 않습니다. 실제 병합 게이트는 후속 단계입니다.

## 개별 보류와 전체 중지

가상 예제의 101을 `next`로 점유한 뒤 자원 부족을 이유로 `block`합니다. 102는 101이 끝나지 않아 기다리고, 다음 `next`는 독립적인 103을 반환해야 합니다. 완료된 이슈는 다시 점유하지 않습니다.

공통 인증 장애 또는 사용자 중지는 `stop`으로 기록합니다. 이때 `next`가 새 작업을 시작해서는 안 됩니다. `resume` 후에는 기존 점유를 이어가며 새 시도로 계산하지 않습니다. 개별 보류 상태는 전체 재개만으로 풀리지 않습니다.

101의 재개 조건을 총괄이 확인한 후 `retry`로 보류를 해제합니다. 103이 이미 완료되고 활성 점유가 없다면 `next`로 101을 다시 점유할 수 있습니다. 101 완료 기록 후 102의 의존 대기가 해제됩니다.

누락되거나 순환하는 의존성은 실행 불가 사유를 남기며 독립 이슈의 진행을 막지 않습니다. 보류된 이슈만 남은 묶음을 전체 완료로 표시하지 않습니다.

## 보관 후 새 묶음 시작

저장소에는 동시에 하나의 진행 묶음만 허용합니다. 중지 또는 시간 만료 상태도 미완료 묶음이므로 다른 run ID를 만들어 우회할 수 없습니다. 작업을 계속 재개할 수 없거나 새 입력이 필요하면 이유를 남겨 `archive`한 후 다른 식별자로 초기화합니다.

```sh
node harness/cli.js status --repo-root . --run demo
node harness/cli.js archive --repo-root . --run demo --revision N --reason "새 입력 검토를 위해 기존 묶음 보관"
node harness/cli.js init --repo-root . --run demo-2 --snapshot harness/fixtures/demo.json
```

`N`은 바로 앞 상태에서 읽은 순번으로 바꿉니다. 보관은 미완료 작업을 성공으로 바꾸지 않습니다. 새 묶음은 총괄이 현재 승인과 외부 상태를 다시 확인한 후 명시적으로 시작합니다.

## 파일 저장과 복구

체크포인트는 Git에서 제외된 `.harness/runs/`에 저장합니다. 저장소 단위 `.harness/locks/queue.lock`을 사용해 모든 쓰기를 직렬화하고, 저장된 변경 순번이 명령의 예상 순번과 일치할 때만 같은 디렉터리의 임시 파일을 rename하여 교체합니다.

`status`는 마지막으로 저장된 상태를 읽는 명령입니다. 시계의 시간 상한 도달을 상태에 반영하려면 `next`를 호출합니다. `next`는 기한이 지난 묶음에서 새 작업을 반환하지 않습니다.

지원하지 않는 버전, 손상 JSON, 잘못된 식별자와 저장 경로, 저장소 밖을 가리키는 심볼릭 링크는 거절합니다. 읽기·검증 오류를 새 빈 상태로 덮어쓰지 않습니다. 프로세스를 다시 시작해도 마지막으로 저장된 상태를 사용합니다.

체크포인트의 절대 상한은 4MiB입니다. 일반 변경은 4MiB에서 128KiB를 남기고, 재개·시간 만료 기록은 120KiB를 남깁니다. 정상 명령으로 저장한 체크포인트는 일반 변경의 한도에 도달해도 최대 길이의 사유를 기록해 `archive`할 수 있도록 공간을 예약합니다. 한도를 넘는 일반 변경은 기존 상태를 보존한 채 거절하므로, 마지막으로 저장된 상태를 읽어 재개하거나 보관한 뒤 새 묶음으로 이어갑니다. 이력은 공간 확보를 위해 자동 삭제하지 않습니다.

파일 교체 후 동기화 실패는 `COMMIT_OUTCOME_UNKNOWN`, 잠금 정리 실패는 `LOCK_CLEANUP_ERROR`로 알립니다. 이런 오류는 변경이 이미 저장됐을 수 있으므로 `status`로 실제 상태와 순번을 다시 읽은 뒤 대응합니다.

프로세스 강제 종료로 잠금이 남았다면 다음 변경은 실패합니다. 프로그램이 실행 중인 잠금을 잘못 지우지 않도록 자동 만료나 자동 삭제는 하지 않습니다. 총괄이 관련 프로세스가 끝났는지 확인하고 체크포인트와 잠금을 보존한 뒤, 남은 잠금만 명시적으로 정리합니다. 체크포인트를 읽어 버전과 순번을 확인한 후 같은 run ID로 재개합니다. 확인할 수 없는 잠금은 그대로 두고 공통 장애로 중지합니다.

이 단계는 로컬 큐의 상태 복구를 다룹니다. 실제 PR 생성·병합의 중복 방지와 실행 에이전트의 취소·복구는 외부 상태 어댑터와 실행기를 연결할 때 검증합니다.
